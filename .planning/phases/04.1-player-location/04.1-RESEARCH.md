## Summary

No new libraries, no packages, no external dependencies. This is four small edits in existing files: `Listings.lua` (guard the read), `UI/Table.lua` (row FontString + tooltip right text), `Preview.lua` (zones on group members), plus new harness checks outside the repo.

The game supplies the data already. `LfgSearchResultPlayerInfo.areaName` is `cstring`, `Nilable = true` (`LFGListInfoDocumentation.lua:1023`). The struct has no per-field secret annotation, but the function `GetSearchResultPlayerInfo` is flagged `SecretInChatMessagingLockdown = true` (`LFGListInfoDocumentation.lua:431`), so any field, areaName included, can arrive secret during lockdown. Blizzard's own finder never displays `areaName`: the only matches in the whole source tree are the API doc line, and `Blizzard_LFGVanilla_Browse.lua` reads `GetSearchResultPlayerInfo` only for level/class/roles (line 380) and for the tooltip's member rows, which show name, level and role only (lines 648-660). So there is no native precedent to copy; the look is our UI-SPEC (stock grey small font, tooltip double line).

**Primary recommendation:** Implement exactly the UI-SPEC; guard with `Secret()` at the read, and keep every zone read downstream as a plain `type(z) == "string" and z ~= ""` check (the value is already clean after `Member()`).

## Integration Points (file:line, current code)

1. **`Listings.lua:49-75` `Member()`**: `area = p.areaName` at line 68 is unguarded. Secret check at line 54 skips the member for name/level/classFilename/assignedRole. Change line 68 to `area = (type(p.areaName) == "string" and not Secret(p.areaName) and p.areaName ~= "") and p.areaName or nil`. Order matters: test `Secret` before comparing `~= ""` (comparing a secret string errors); `type()` on a secret is safe. `spec = p.specName` (line 67) has the same hole; guard it the same way (trivial, and a secret spec would otherwise reach string concatenation in `ExtrasTooltip` line 583 and `row.sub:SetText`).
2. **`UI/Table.lua:848-853` BuildRow**: add before `row.comment`:
   `row.zone = W.Text(cells.activity, "GameFontDisableSmall", 10)`, `row.zone:SetPoint("TOPLEFT", 0, -19)`, `row.zone:SetMaxLines(1)`. `W.Text` already does `SetWordWrap(false)` (Widgets.lua:224) and left-justify. Do **not** keep the `row.comment` `SetPoint("TOPLEFT", 0, -19)` as the only anchor: FillRow re-anchors it. Keep `SetPoint("RIGHT", 0, 0)` on the comment, but note `ClearAllPoints` removes it too, so FillRow must re-add both points every fill.
3. **`UI/Table.lua:1079-1081` FillRow**: after `row.activity:SetText(...)`:
   ```lua
   local zone = (not l.mine) and who.area or nil   -- who = l.leader, defined earlier in FillRow
   if type(zone) ~= "string" or zone == "" then zone = nil end
   row.comment:ClearAllPoints()
   if zone then
       row.zone:SetWidth(0); row.zone:SetText(zone)
       local cap = ZONE_MAX
       local cw = row.cells.activity:GetWidth()
       if cw and cw > 0 then cap = min(ZONE_MAX, floor(cw * ZONE_FRAC)) end
       row.zone:SetWidth(max(1, min(cap, row.zone:GetStringWidth())))
       row.zone:Show()
       row.comment:SetPoint("TOPLEFT", row.zone, "TOPRIGHT", ZONE_GAP, 0)
   else
       row.zone:SetText(""); row.zone:Hide()
       row.comment:SetPoint("TOPLEFT", 0, -19)
   end
   row.comment:SetPoint("RIGHT", 0, 0)
   row.comment:SetText(l.comment or "")
   ```
   Verify `who` is in scope there (it is used at line 1049/1104, so yes).
4. **`UI/Table.lua:1098-1108` colours**: add `row.zone` to the `texts` list (greyed -> `W.DELISTED`, loop uses `pairs`, tolerant of nil `row.gs`), and in the non-greyed branch add `W.SetColor(row.zone, W.GRAY)` next to the comment line. Colour resets on every fill are mandatory (pooled rows).
5. **`UI/Table.lua:508-517` StockTooltip**: leader line `tip.line(left, WHITE, false, ns.GEAR_SCORE and ("GS " .. GSLine(who)) or nil)` and member lines (514) pass `right` only when GS is on. Add a local helper:
   ```lua
   local function RightText(m, gs)
       local z = (type(m.area) == "string" and m.area ~= "") and (ColorCode(W.GRAY) .. m.area .. "|r") or nil
       if z and gs then return z .. "  " .. gs end
       return z or gs
   end
   ```
   Use it at both call sites (`RightText(who, ns.GEAR_SCORE and ("GS " .. GSLine(who)) or nil)`; members `RightText(m, ns.GEAR_SCORE and GSLine(m) or nil)`). Do this only inside the `group` branch for the leader line: for a solo listing the zone is already in `ExtrasTooltip` (line 583) and must not duplicate. Also skip when `l.mine` (D-05). `TipWriter.line` (324-345) treats any non-nil `right` as a double line and passes white (1,1,1) for the right colour; the embedded `|cff...|r` code recolours the zone, and GS keeps its own colour codes/white. Right text is never wrapped by us; long zones widen the tooltip (acceptable, D-10).
6. **`UI/Table.lua:781-795` Layout**: no change; it anchors cells, not their children. The activity cell's width is only known after layout; it is set by two points (LEFT/RIGHT, lines 793-794), so `GetWidth()` can return 0 or a stale value on the very first fill. Fall back to `ZONE_MAX`; the UI-SPEC accepts this. If a width change must refresh zones (458 vs 620 px), the table's existing relayout/refill path already re-runs FillRow; confirm that during planning rather than adding a Layout hook.
7. **`Preview.lua:78-94` Members, 120-128 Group**: member strings are `Name:CLASS:level:ROLE[:gs]` with the pattern at line 81. Cheapest shape: optional trailing `@Zone` on the string, e.g. `"Brannoc:WARRIOR:21:TANK:22.4@Stranglethorn Vale"`. Change the pattern to capture the gs part up to `@` (`:?(~?[%d%.]*)@?(.*)$`) and set `area = zone ~= "" and zone or nil` in the member table. Zone names may contain `'` and spaces but not `:` or `@`, which are safe. `Solo` already takes `area` (line 131/143). `P.party` untouched (D-13). Required coverage: leader+members all zoned; leader zoned but some members not; one group with no `@` at all; "Stranglethorn Vale" and "The Temple of Atal'Hakkar"; one zoned group that also has a comment (most do).

## Common Pitfalls

1. **Stale re-anchor on pooled rows.** `ClearAllPoints` on `row.comment` every fill, in both branches, and re-add the RIGHT point. Forgetting leaves a comment anchored to a hidden zone after a recycle.
2. **Hidden zone still anchors the comment.** When no zone, anchor to the cell, not to `row.zone`.
3. **Greyed colour.** Without adding `row.zone` to `texts`, greyed rows keep a bright zone; normal rows would keep the greyed colour after reuse unless `W.GRAY` is set in the else branch.
4. **Own row.** `l.mine` must give no zone even though its leader has `area` from the game (`Member()` reads it). Check `l.mine` in FillRow and in the tooltip helper.
5. **Secret areaName.** Guard at the read; never compare, concatenate or `GetStringWidth` a secret. Drop only the zone; the existing line-54 skip must not gain `p.areaName`.
6. **Width measure.** `GetStringWidth()` on a FontString returns the natural width of the current text with word-wrap off, but a width left over from the previous fill can interfere, so `SetWidth(0)` then `SetText` then measure. On a fresh frame before layout, the cell width may be 0: use `ZONE_MAX`.
7. **Solo tooltip duplicate.** Do not add the zone to the solo leader line; `ExtrasTooltip` already writes "spec, zone". Over-10 groups: members are not looped (line 511), so no member zones; the leader's zone still shows.
8. **GS-on combination.** Order is zone, two spaces, GS; leader keeps its "GS " prefix. GS is off in this release, so test both via the `--gs` mode.
9. **Pairs/ipairs with nil.** `texts` uses `pairs` (fine with nil `row.gs`); do not switch it to `ipairs`.
10. **Taint.** Everything here is our own frames and tooltip; no Blizzard frame is touched.

## Don't Hand-Roll

Use `W.Text`, `W.SetColor`, `ColorCode`, the existing `TipWriter` right-text path. Do not build a custom truncation routine: FontString width plus `SetWordWrap(false)`/`SetMaxLines(1)` truncates with an ellipsis natively.
